## Code fix

Better Auth and the public `/api/auth/providers` endpoint share one
server-side credential-pair check. The endpoint exposes only availability
booleans and existing public OIDC metadata, with `Cache-Control: no-store`.
Sign-in and sign-up fetch these capabilities at runtime, start with social
providers hidden, and ignore aborted discovery responses. Email/password,
passkey, and existing OAuth error/timeout recovery remain independent.

Callback recovery is also addressed: social requests return failures to their
sign-in/sign-up form while retaining the validated destination. Missing or
invalid OAuth state has a canonical login fallback. Forms map error codes to
bounded, actionable messages and never display provider-controlled
`error_description`. Better Auth does provide `/api/auth/error`; its production
default redirects to the homepage with query errors, losing the login context.
The defect is not a missing API route. Existing local-email verification and
account-linking safeguards are deliberately preserved.

The obsolete `NEXT_PUBLIC_OAUTH_GOOGLE_ENABLED` and
`NEXT_PUBLIC_OAUTH_GITHUB_ENABLED` flags are no longer required. Both members
of the matching server credential pair must be configured; missing or
whitespace-only credentials keep the provider unavailable.

### Newly verified server-side blocker

The real production Google button starts an HTTP 500 before reaching Google.
Sanitized Vercel runtime diagnostics identify PostgreSQL `22001`, "value too
long for type character varying(255)". The initial migration defines
`verification.value` as `VARCHAR(255)`, but Better Auth 1.6.25 stores serialized
OAuth state there, including a 128-character PKCE verifier, destinations,
expiry, and the separate OAuth state value.

Root independently reproduced this with the installed native Better Auth
handler and a randomly named schema in local `latexy_test`, with synthetic
credentials and no external provider exchange. Original column: HTTP 500.
After widening only `verification.value` to `TEXT`: HTTP 200 and a Google
authorization URL with exactly `openid`, `email`, `profile`. Ordinary
`/workspace` stored 290 characters; a 4,114-character destination stored 8,502.
The diagnostic removed only its own random schema. No production data was
changed by that diagnostic.

Migration `0059` widens the field without discarding records. Its downgrade
must refuse oversized existing records, never silently truncate or delete
them. State cookies, PKCE, nonce validation, and account-linking safeguards
remain unchanged. Migration CI/main rollout and real sign-in acceptance are
still required; availability alone is not proof of a working OAuth exchange.

Root pre-publication checks for this follow-up passed: 1,057 frontend tests in
166 files; focused runtime/callback/ownership checks (25); TypeScript and
ESLint; production build and artifact validation with explicit HTTPS build
metadata and synthetic signing secret; and six actual PostgreSQL storage /
migration-integrity regressions with warning-as-error checks. The original
unset-build-origin run refused HTTP as designed; it was not reported as a
passing build. An initial regression hit a prepared-statement cache tied to
its temporary schema; isolated uncached migration-test connections fixed that
test-only issue without changing production connection caching. Independent
read-only review confirmed data preservation and homepage-only proof scope.
