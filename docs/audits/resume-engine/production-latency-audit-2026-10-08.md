# Production latency audit — 8 October 2026

Production does not meet the engine's latency targets. This pass measured the real public site and an authorized, newly created ordinary test account. It did not change roles, borrow customer credentials, bypass quota, make a payment, merge the engine PR, or deploy a migration. Work remains on `codex/resume-engine`, PR #1833.

Screenshots show the optimization and cover-letter source editors **still loading** at heading capture. Heading readiness cannot establish full feature readiness. No browser runtime or console errors appeared in the successful saved-account run or feature-navigation run. Several `net::ERR_ABORTED` requests occurred during navigation/prefetch cancellation; these alone are not failed user actions. The in-app browser initially showed `Failed to fetch` on signup's workspace; Retry recovered, and separate Chrome loaded the account/library and 61-template catalog. Paid optimization/review quality, generated cover-letter/interview output, external account integrations, third-party job application submissions, and the undeployed new no-code engine remain **uncertified in production**. No blanket “all features fast” or “no bugs” claim is supported.

## Changes implemented in this pass

1. Quick ATS: score the first valid source immediately; debounce subsequent typing by 600 ms with a two-second background interval. Deduplicate matching active/completed inputs, cancel obsolete requests and retain stale-response guards. Source and job description both participate in identity. Remove the obsolete ten-second tooltip.
2. New Resume: render title, import and blank-start controls while templates are loading. The existing catalog skeleton now appears inside the form rather than blocking all controls. Authentication, owner boundaries and creation guards remain enforced.
3. Artifact uploads: publish PDF and optional SyncTeX concurrently in a fixed two-thread executor. Validate/read SyncTeX before publication; join both writes before propagating failure. Immutable conditional writes, owner/epoch publication fences, retention and checksum validation remain required.
4. Feature admission: conversion, cover-letter, interview, GitHub import, JD analysis, deep analysis, resume embeddings, comment mentions and share-view notification submissions now await the existing bounded broker helper. Synchronous Modal/Celery SDK calls run outside the API event loop; normal payloads and durable dispatch uncertainty handling remain intact. This removes a verified source-level event-loop stall. The separate provider/terminal-state defect below explains the stranded conversion; moving submission off the event loop alone would not repair it.
5. Conversion runtime: platform calls explicitly use the configured platform endpoint **and model**. OpenAI BYOK calls use the OpenAI origin and model explicitly, so a process-wide compatibility endpoint cannot receive the user's key. SDK and task retries are disabled on this legacy path, which has no paid-stage replay ledger. Provider errors, timeouts and invalid output now select an owned terminal failure and the existing once-only quota refund instead of an eager retry loop. A dropped failure event does not suppress an accepted failure's refund; a rejected result cannot refund another owner. This repairs the reproduced failure path without making an untested live provider success claim.
6. Modal worker logging: prepare the application JSON logging handler once before worker runtime/admission. These workers do not pass through API logging startup; the production worker logs lacked the informational timing records needed to separate phases. The helper respects configured log level and uses the existing diagnostic/privacy filters. A clean-process test observes one structured slow-phase record and verifies repeated preparation does not duplicate handlers.

The [Boto3 client guidance](https://docs.aws.amazon.com/boto3/latest/guide/clients.html) supports sharing clients across threads, with caveats about creation and custom mutation. The storage singleton already locks creation; this change adds no shared client metadata/event-hook mutation. The paired benchmark uses the real isolated S3-compatible store, immutable writes and readback, alternating 30 serial/concurrent pairs with **explicitly simulated 40-ms delay per PUT**: serial p50 299.64 ms, concurrent p50 161.09 ms. Raw p95 values are 2,131.47 and 621.40 ms under uncontrolled host load. These are upload-phase experiments, not a production or whole-engine speedup.
