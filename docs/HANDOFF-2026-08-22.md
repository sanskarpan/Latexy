## 4. The commit/PR procedure (use verbatim when asked to land work)

1. **Create GitHub issues first** — one per logical fix/feature, via `gh issue create --label "bug"` (or an appropriate label). Write a real description (root cause + fix), not a placeholder.
2. **One commit per file.** Never batch multiple files into one commit. `git add <single-file> && git commit -m "..."`.
3. **Every commit message includes `closes #N`** (or `part of #N` for a file that serves a secondary issue too — see the pattern in the merged history for files that were genuinely dual-purpose, e.g. `tracker/page.tsx` in this round).
4. **No AI/assistant mentions anywhere** — not in commits, issues, or PR bodies.
5. **Group commits into topic sub-branches**, one per issue/epic, each with its own PR. In this round the flow was: commit everything to one integration branch first (`fix/<topic>-integration`), then cherry-pick per-epic commit groups onto fresh sub-branches off `main`, push, and open each sub-branch's PR *against the integration branch* (not `main`).
6. **Merge the sub-branch PRs into the integration branch.** Note: sub-branches built from cherry-picked commits can fail their *own* standalone CI if they reference a file introduced in a different epic's branch (e.g. a page importing `useRequireAuth` before that hook's own commit exists on that branch) — this is expected and not a blocker. The integration branch's CI, after all sub-PRs land, is the real gate; it has the full file set and must be green.
7. **Open the final integration → `main` PR**, body referencing/closing all epic issues (`Closes #A, #B, ...`). Confirm CI is green on that PR too before merging.
8. **Merge to `main`. Verify CI on `main` itself** (a push to `main` triggers its own run — don't assume the PR's pre-merge check is identical).
9. **Deploy if asked to**: frontend is automatic (Vercel watches `main`); backend is manual — see §6.
10. **Never manually close an issue** — let the `closes #N` keyword do it on merge. If you close one by mistake, don't worry about un-closing it, just note it.

Whether you actually get to (and including) step 8's merge, or stop earlier and hand PRs to the user to merge themselves, depends entirely on what the user asked for in that specific request — re-read §3.

## 5. Gotchas discovered this session (save yourself the debugging time)

- **SSH (port 22) is blocked in this sandbox.** `git push`/`git fetch` over the configured `git@github.com-sanskar:...` remote will hang and time out. Workaround: `gh auth setup-git` (registers `gh`'s HTTPS credential helper), then push/fetch using an explicit HTTPS URL, e.g. `git push https://github.com/sanskarpan/Latexy.git <branch>:<branch>`. `gh` CLI commands (`gh issue create`, `gh pr create`, etc.) work fine regardless — they don't go through the git remote at all.
- **`./scripts/dev.sh status`/`infra` can report MinIO as up when it isn't.** If PDF-related flows fail locally, check with `docker ps --filter name=minio` directly; if missing, `docker compose -f docker-compose.yml up -d minio minio-init`.
- **Rate limiting is enabled by default; local dev disables it** via `RATE_LIMIT_ENABLED=false` baked into `dev.sh`'s env for the backend process. Production has it on — don't hammer `latexy.xyz` with rapid repeated Playwright sessions when smoke-testing; space requests out or you'll see transient timeouts that look like app bugs but are just backend/edge throttling (confirmed harmless via retry during this session's prod smoke test).
- **Modal deploys take ~30 minutes** (image build), and can time out a foreground shell call — run them with `run_in_background: true` and wait for the notification rather than polling tightly.
- **A fresh Modal deploy means cold containers** for a few minutes afterward; don't be alarmed by one-off timeouts in the first post-deploy smoke check — retry before concluding it's a real regression.
- **Playwright is available via the Node module directly**, not a CLI: `require('/Users/sanskar/node_modules/playwright')` in a throwaway script (see this session's scratchpad for two working examples — local dev E2E and prod smoke — though scratchpad contents are ephemeral and may not persist into your session).
